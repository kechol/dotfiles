# handoff

現在の作業状態を、**次のセッションが状況の再調査から始めなくて済む**引き継ぎプロンプトに変換する。あなたは「記録役」であり、引き継ぎ対象のタスク自体はここで進めない。成果物は、ユーザーがそのままコピーして次のセッションに貼れる日本語のプロンプトである。

引き継ぎで最も抜けやすいのは 3 つ — **未コミットの変更が何のためのものか**、**どこまで検証済みか**、**迷ったときの判断基準**。この 3 つが無いと、次のセッションは差分を読み直し、テストを流し直し、そして勝手に判断する。だからこのスキルは、この 3 つを必ず埋める。

引き継ぎ先は人間とは限らない。**次のセッションの AI エージェントが読んで即座に動ける**ことを到達点にする。

## Step 1. 状態を実測する（会話の記憶より先に）

会話の記憶だけで「到達点」を書かない。記憶は完了していないものを完了と書く。まず実値を取る。

```sh
git rev-parse --show-toplevel
git rev-parse --abbrev-ref HEAD
git log -1 --format='%h %s (%ad)' --date=short
git status --short
git rev-list --count @{u}..HEAD
git stash list
```

- **git リポジトリでない**（`rev-parse` が失敗）なら、作業対象は「絶対パス + git 管理外」と書き、以降の git 由来の項目は全て省略ではなく「git 管理外のため不明」と明記する。
- **upstream が無い**（`@{u}` が失敗）なら未 push 件数の行は「upstream 未設定」と書く。エラーを無視して黙って落とさない。
- **直近の作業範囲**を掴むなら `git log --oneline -10` と `git diff --stat` も見る。会話で「やった」と言ったことが実際にコミットされているか、ここで突き合わせる。食い違ったら**実測を採用**する。
- 検出したテストコマンドを実際に流して現在の緑/赤を確認できるなら、その結果を引き継ぎに書く。流していないなら「未検証」と書く。**流していないものを緑と書かない。**

## Step 2. プロジェクトの文脈を検出する

パスもコマンドも**実行時に検出する**。特定プロジェクトの構造を前提にしない。

**規約ファイル**（存在するものだけ列挙する）:

```sh
ls CLAUDE.md AGENTS.md CONTRIBUTING.md README.md docs/README.md .cursorrules 2>/dev/null
ls .claude/ docs/ 2>/dev/null
```

**タスク管理**（存在するものだけ）:

```sh
ls TODO.md ROADMAP.md docs/TODO.md docs/backlog.md docs/decisions.md 2>/dev/null
```

GitHub リポジトリなら `gh issue list` / `gh pr view` も候補。該当タスクの記述が見つかったら、**そこから直接引用**する（言い換えると情報が痩せる）。

**実行方法**は規約ファイルとビルド定義（`package.json` の scripts、`Makefile`、`justfile`、`pyproject.toml`、`Cargo.toml` など）から拾い、このセッションで**実際に使ったコマンド**を優先する。実際に動いたコマンドが最も信頼できる。

どれも見つからない項目は空欄にせず「不明」と書く。次のセッションは、書かれていないものを「無い」と誤読するより「不明」と知らされたほうが正しく動ける。

## Step 3. 生成前に確認する

以下は勝手に決めず、`AskUserQuestion` でユーザーに確認する。

- **作業ツリーが clean でない場合**: 未コミットの変更を一覧して見せ、「この状態のまま引き継ぐ」か「コミット（または stash）してから引き継ぐ」かを確認する。中途半端な作業ツリーを黙って渡さない。そのまま引き継ぐなら、**各変更が何のためのものか**を引き継ぎ本文に書く（これが最も抜けやすい）。
- **引き継ぎ先が同じ領域の続きか、別領域か**: 別領域なら、相手が知らない前提（設計判断の経緯、既知の落とし穴、用語）を厚く書く。同じ領域の続きなら簡潔でよい。
- **タスク管理ファイルがある場合**: 該当タスクに「着手中」の印があるか確認し、無ければ付けるようユーザーに促す。印の書式はそのファイルの既存の慣習に合わせる（勝手な書式を導入しない）。

## Step 4. 出力先を決める

**勝手にディレクトリを作らない。** 次の順で決める。

1. 規約ファイル（CLAUDE.md 等）に生成物の置き場所が書かれていれば、それに従う。
2. 無ければ、既存の一時ディレクトリ（`tmp/`、`.output/` など）を探し、`git check-ignore -q <dir>` で ignore 済みか確認してから使う。ignore されていなければリポジトリを汚すので使わない。
3. どちらも無ければ**チャットに全文を出すだけ**にし、ファイルは作らない。

ファイルに書く場合も**チャットに全文を出す**。ユーザーはそのままコピーして次のセッションに貼るため。

## Step 5. 引き継ぎプロンプトを生成する

下のテンプレートに沿って日本語で書く。該当しない節は削り、空節を作らない。**埋まらない項目は「不明」と明記する**（黙って省略しない）。

```md
# 引き継ぎ: {現在地と次の一手を一文で}

{このプロンプトを受け取ったセッションが最初に理解すべきこと。何のタスクの、どの段階か。2〜3文}

## 作業対象
- リポジトリ: `{絶対パス}`（{git 管理 / git 管理外}）
- ブランチ: `{branch}` / 直近コミット: `{sha} {件名}`
- origin との差: {未 push N 件 / upstream 未設定 / 不明}
- 作業ツリー: {clean / 未コミット N 件}

{未コミットがある場合、ファイルごとに「何のための変更か」を1行で。
 例: `src/auth/token.ts` — リフレッシュトークンの有効期限を 7d → 30d。仕様確認待ちで未コミット}

## 最初に読むもの
1. `{規約ファイル}` — {何が書いてあるか}
2. `{作業領域の文書}` — {なぜ読む必要があるか}
{存在するものだけ。無ければ「プロジェクト規約ファイルは無い」と書く}

## 前セッションの到達点
- **完了**: {コミット SHA や実ファイルで裏が取れているものだけ}
- **部分完了**: {どこまでで、何が残っているか}
- **確定した方針**: {なぜそう決めたかを1行添える。理由が無いと次のセッションが覆す}
- **未解決の論点**: {判断保留のもの。保留の理由も}

## 次にやること
1. {タスク}
   - 受け入れ基準: {検証可能な形で}
{タスク管理ファイルがあれば該当箇所を引用し、その所在も書く}

## 環境・実行の制約
- ビルド/テスト: `{実際に使ったコマンド}`
- 外部依存: {DB・LLM・エミュレータ・認証など。起動方法と前提}
- リソース制約: {同時実行不可、実行に N 分かかる、など}

## 完了条件
{何をもって終わりとするか。必ず検証可能な形で書く}

## 中断条件
{どうなったら止めて報告するか。ここが無いと、次のセッションは行き詰まっても走り続ける}

## 検証方法
{テスト・リンタ・実ファイル・外部ツールの出力を根拠にする。
 「実装した本人の自己申告を根拠にしない」ことを明記する}

## 判断基準（迷ったとき）
{選択肢が生じうる箇所と、どちらを選ぶか。
 例: 「既存 API の互換を壊す変更が必要になったら、壊さない側を選び、理由を報告に書く」}

## 禁止事項
- コミット/push: {可否と条件}
- 触ってはいけない領域: {ファイル・ディレクトリ・設定}

## 報告
{何を、どこに書くか（チャット / ファイルパス / タスク管理ファイルへの追記）}
```

「判断基準」を空にしない。ここが空だと次のセッションに判断を丸投げすることになり、意図しない方向に進む。

## 無人実行モード

`--unattended` 相当（「夜間実行」「寝ている間に」「質問できない」）の指定があれば、上のテンプレートに次を追加する。

**時間ガード**（`## 時間ガード` として先頭近くに置く）:

```md
起動直後に `date` で現在時刻を確認し、打ち切り時刻を {N 時間後 / 指定時刻} と決める。
各作業の着手前に、残り時間で完了できるか判断する。無理なら着手せず報告フェーズへ移る。
```

**質問できない前提**: 判断が要る箇所は、選択肢と決定基準を**先に**書き切る。「迷ったら聞く」は使えない。「迷ったら {保守的な側} を選び、理由を報告に書く」に置き換える。

**憶測の禁止**: 「成功した」「通った」と書く前に、実ファイル・実コマンド出力で裏を取る旨を明記する。長時間の無人実行では、この一文の有無で報告の信頼性が変わる。

**中断時の後始末**: 中途半端な状態で終わるとき何を残すか（作業ブランチ、途中経過のレポート、タスク管理ファイルへの NOTE 追記）を書く。次に人間が見たときに状況が分かる形で終わらせる。

## 品質基準（出す前に確認する）

- **git の実値が入っているか。** ブランチ名・コミット SHA・未コミット件数が具体値で書かれているか（プレースホルダのままでないか）。
- **完了と部分完了が区別されているか。** 実測で裏が取れていないものを完了と書いていないか。
- **未コミットの変更に「何のため」が書かれているか。**
- **どこまで検証済みかが書かれているか。** 未検証なら未検証と書かれているか。
- **判断基準があるか。** 次のセッションが迷いうる箇所に、先回りした基準があるか。
- **完了条件が検証可能か。** 「良い感じになったら」のような自己採点になっていないか。
- **不明が「不明」と書かれているか。** 埋まらなかった項目が黙って消えていないか。
- **これ単体で動けるか。** このプロンプトだけを渡された相手が、前の会話を見ずに作業を始められるか。

## 禁止事項

- 会話の記憶だけで到達点を書かない。`git log` と実ファイルで裏を取る。
- 完了していないことを完了として書かない。部分完了は部分完了と書く。
- 次のセッションに判断を丸投げしない。迷ったときの基準を先に書く。
- 生成先のディレクトリを勝手に作らない（Step 4 に従う）。
- 引き継ぎ対象のタスク自体をここで進めない。あなたは記録役である。
