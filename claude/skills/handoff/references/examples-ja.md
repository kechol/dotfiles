# 完成例

生成物の粒度とトーンの基準。**内容は例であり、値はすべて実行時に検出したものへ置き換える。**

読みどころは、テンプレートの節名ではなく「どこまで具体的に書くか」。特に未コミット変更の説明、確定した方針に添えた理由、判断基準の書き方に注目する。

---

## 例 1: 通常の引き継ぎ（未コミットあり・同じ領域の続き）

規約ファイル（CLAUDE.md）と TODO.md があるプロジェクト。作業ツリーが汚れた状態で、ユーザーが「このまま引き継ぐ」を選んだケース。

````md
# 引き継ぎ: 認証トークンのリフレッシュ実装（サーバ側完了・クライアント側未着手）

`api-gateway` のトークン更新まわりを実装中。サーバ側のエンドポイントとテストは完了してコミット済み。クライアント SDK 側の自動リフレッシュが未着手で、その前段のリファクタが未コミットのまま残っている。

## 作業対象
- リポジトリ: `/Users/foo/src/api-gateway`（git 管理）
- ブランチ: `feat/token-refresh` / 直近コミット: `a3f91c2 feat(auth): add /token/refresh endpoint`
- origin との差: 未 push 2 件
- 作業ツリー: 未コミット 3 件

未コミットの内訳:
- `sdk/src/client.ts` — リクエスト送出を `request()` に一本化するリファクタ。リフレッシュ処理を差し込む場所を作るための準備。**動作は変えていない**が SDK のテスト未実行
- `sdk/src/types.ts` — `AuthState` に `expiresAt` を追加。上記から呼ぶ
- `tmp/scratch.http` — 手動確認用。コミット不要、消してよい

## 最初に読むもの
1. `CLAUDE.md` — コミット規約とテストの流し方。特に「テストが緑でないコミットは禁止」
2. `docs/auth.md` — トークンの寿命と失効の設計。`expiresAt` の意味はここ
3. `TODO.md` の「認証」節 — 今回のタスク T-12 / T-13

## 前セッションの到達点
- **完了**: `POST /token/refresh`（`a3f91c2`）。サーバ側テスト 24 件が緑（`npm test -w server` で確認済み）
- **部分完了**: SDK のリファクタ（上記未コミット 2 件）。書いたがテスト未実行、レビューもしていない
- **確定した方針**: リフレッシュはリクエスト失敗時（401）ではなく**期限の 60 秒前に先回り**して行う。401 起点だとリトライで実質 2 倍のリクエストが出るため
- **未解決の論点**: 並行リクエスト中にリフレッシュが走った場合の扱い。単一の in-flight Promise を共有する案が有力だが未検証

## 次にやること
1. 未コミット分の SDK テストを流し、緑ならコミットする
   - 受け入れ基準: `npm test -w sdk` が終了コード 0
2. `client.ts` に自動リフレッシュを実装（T-13）
   - 受け入れ基準: 期限 60 秒前に `/token/refresh` が 1 回だけ呼ばれることを検証するテストが通る。並行 3 リクエストでもリフレッシュは 1 回

## 環境・実行の制約
- テスト: `npm test -w server` / `npm test -w sdk`（リポジトリルートから）
- 型チェック: `npm run typecheck`
- ローカル API は `docker compose up -d` が必要（Postgres を使う）。テストは不要

## 完了条件
T-13 の受け入れ基準を満たすテストが緑で、`npm run typecheck` が通り、コミット済み。

## 中断条件
- 並行リクエスト時の挙動が設計を変えないと解けないと分かったとき（`docs/auth.md` の変更が必要になる）
- 既存のサーバ側テストが赤くなったとき

## 検証方法
`npm test -w sdk` と `npm run typecheck` の実際の出力を根拠にする。実装した本人の「動くはず」を根拠にしない。並行リクエストの挙動はテストで示す（手動確認で代替しない）。

## 判断基準（迷ったとき）
- リフレッシュの粒度で迷ったら、**リクエスト数が少ない側**を選ぶ（先回り方式を選んだ理由と同じ）
- `docs/auth.md` の設計を変えたくなったら、変えずに実装できる案を優先し、無理なら中断して報告する

## 禁止事項
- コミットは可。**push はしない**（PR の粒度をユーザーが決めるため）
- `server/` 配下は今回触らない（サーバ側は完了済み）

## 報告
チャットに、実施内容・テスト結果・未解決のまま残した論点を書く。`TODO.md` の T-12 / T-13 に結果を追記する。
````

## 例 2: 無人実行モード（夜間・質問できない）

規約ファイルが無いプロジェクト。時間ガードと憶測禁止が入り、判断基準が先回りで書かれている。

````md
# 夜間実行: 画像処理バッチのベンチマーク取得

`img-pipeline`（`/Users/foo/src/img-pipeline`）で、**人間が就寝中**に 3 パターンのベンチマークを取得し、朝までに結果を報告する。質問はできない。判断が要る箇所は「判断基準」に従う。**憶測で「速くなった」と書かず、必ず実測ログで裏を取る。**

## 時間ガード
起動直後に `date` で現在時刻を確認し、**打ち切り時刻を起動から 6 時間後**と決める。各ベンチ（1 本 約40分）の着手前に、残り時間で完了できるか判断する。無理なら着手せず報告フェーズへ移る。

## 作業対象
- リポジトリ: `/Users/foo/src/img-pipeline`（git 管理）
- ブランチ: `main` / 直近コミット: `7d10ab4 perf: parallelize resize stage`
- origin との差: upstream 未設定
- 作業ツリー: clean

## 最初に読むもの
- プロジェクト規約ファイルは無い。実行方法は `Makefile` を読む
- `bench/README.md` — ベンチの起動方法と出力先

## 前セッションの到達点
- **完了**: resize ステージの並列化（`7d10ab4`）。単体テストは緑（`make test` で確認済み）
- **未検証**: 並列化で実際に速くなったかは**未計測**。これが今回のタスク
- **確定した方針**: 計測は 3 回の中央値を採る。単発だとディスクキャッシュの影響が大きいため

## 次にやること
1. `make bench INPUT=bench/data/small` を 3 回（約10分）
2. `make bench INPUT=bench/data/medium` を 3 回（約40分）
3. `make bench INPUT=bench/data/large` を 3 回（約90分）
   - 受け入れ基準: 各サイズについて 3 回分のログが `bench/out/` に残り、中央値が算出できること

## 環境・実行の制約
- 実行は 1 本ずつ。**同時実行するとメモリ不足で落ちる**（16GB マシン）
- 1 本 40〜90 分かかるものがある。バックグラウンドで起動し、完了を待って次へ進む
- 出力は `bench/out/<timestamp>.json`。既存ファイルは消さない（比較に使う）

## 完了条件
3 サイズ × 3 回のログが揃い、`bench/out/summary.md` に中央値と `7d10ab4` 前後の比較が書かれている。

## 中断条件（該当したら記録して報告フェーズへ）
- ベンチが 2 回連続で異常終了した
- 打ち切り時刻に到達した
- 想定外の性能劣化が出た。**夜間のコード修正は行わず**、再現手順を記録して申し送る

## 検証方法
`bench/out/*.json` の実値のみを根拠にする。プロセスが 0 で終了しただけでは完了としない（出力ファイルの存在と中身を確認する）。「速くなった」と書く前に、比較対象の数値を並べて示す。

## 判断基準（迷ったとき）
- large が時間内に終わらないと判断したら、**着手せず small/medium の結果だけで報告する**（中途半端な 1 回分より、揃った 2 サイズのほうが価値がある）
- 数値がばらついて中央値が信用できないと感じたら、回数を増やさず**ばらつきを記録して報告**する（時間を溶かさない）

## 禁止事項
- コードを変更しない（計測のみ）。`bench/out/summary.md` の追加とコミットは可
- 既存のベンチログを消さない

## 報告（`bench/out/summary.md`）
- 各サイズの 3 回分の実測値と中央値
- `7d10ab4` 前後の比較（前の値が無ければ「比較対象なし」と明記）
- 未達・中断があればその理由と、次のセッションへの申し送り

## 中断時の後始末
途中で終わる場合、取れた分だけを `bench/out/summary.md` に書き、冒頭に「未完了: 残りは {サイズ}」と明記する。書きかけのファイルを残さない。
````

## 例から読み取ってほしいこと

- **未コミットの説明は「何を変えたか」でなく「何のための変更か」。** 差分は次のセッションも読める。読めないのは意図。
- **確定した方針には理由を添える。** 理由の無い方針は、次のセッションに覆される。
- **判断基準は選択肢とセットで書く。** 「慎重に判断する」では基準にならない。どちらを選ぶかまで書く。
- **未検証は未検証と書く。** 例 2 の「並列化で速くなったかは未計測」が、そのままタスクの起点になっている。
