# 既存ドキュメントの棚卸しと、決定・タスクの抽出

初期化しただけの空の台帳は使われない。**最初のセッションで既に中身がある**状態にすると運用が立ち上がる。
ただし、勝手に既存ファイルを消したり書き換えたりすると信頼を失う。**提案までがスキルの仕事**で、
移動・削除の実行はユーザーの承認を得てから行う。

## 1. 棚卸し — 何がどこにあるか

```bash
fd -e md --max-depth 2 . | rg -v '^(node_modules|vendor|\.git)' 
wc -l $(fd -e md --max-depth 2 .) 2>/dev/null | sort -rn | head -20
```

`.github/`、`node_modules/`、ライブラリ同梱の LICENSE 類は対象外。見るのは**人が書いたリポジトリ固有の文書**だけ。

### 分類

| 分類 | 例 | 扱い |
|---|---|---|
| 正規のドキュメント | `README.md` `CONTRIBUTING.md` `CHANGELOG.md` `LICENSE` | そのまま。触らない |
| 決定が埋もれている | `ARCHITECTURE.md` `docs/design.md` `ADR/` `RFC/` | decisions への抽出候補（§4） |
| タスクが埋もれている | `TODO.md` `ROADMAP.md` `PLAN.md` | backlog への抽出候補（§5）。**§2 の追跡状態を先に確認する** |
| 使い捨てメモ | `NOTES.md` `SUMMARY.md` `TEST_RESULTS.md` `MEMO.md` | 内容を台帳へ振り分け、残りは削除候補として提案 |
| エージェント指示 | `CLAUDE.md` `AGENTS.md` `.claude/rules/` `.cursor/rules` | 運用ルールの追記先候補 |

### 提案のしかた

見つけたものを表で示し、**それぞれに提案（抽出 / そのまま / 削除候補）と理由**を1行で添える。
削除は自分から実行しない。git に残るとはいえ、消す判断はユーザーのもの。

台帳は backlog と decisions の2つだけで、**行き場のないメモを置くためのディレクトリは作らない**。
どちらにも振り分けられない内容は、残す価値があるかをユーザーに問う。

## 2. 抽出元は git 追跡下のファイルに限る

棚卸しでも抽出でも、**まず追跡状態を確認する**。

```bash
git check-ignore -v <file>              # ignore されているか（されていれば出力あり）
git ls-files --error-unmatch <file>     # 追跡下にあるか
```

`.gitignore` されたファイル（`TODO.md` `NOTES.md` `.prompt` など）は、**意図的に共有対象から
外されていることが多い**。公開リポジトリでは「私的な文脈を commit に持ち込まない」という方針で
ignore されている場合があり、そこから起こした台帳を commit すれば、その方針を破ることになる。

- **ignore されたファイルの中身を、台帳や commit メッセージに移植しない**
- 有用な内容が入っていた場合は、**存在と概要だけをユーザーに伝えて判断を仰ぐ**。
  中身の引用や要約を報告文に貼らない（報告自体が共有経路になりうる）
- 追跡下にないだけで ignore もされていないファイルは、単なる作りかけ。扱いをユーザーに確認する

同じ理由で、`.env` や認証情報を含むファイルも抽出元にしない。

## 3. 抽出の原則

**推測で埋めない。** 台帳の1行は「後で `git log --grep` の起点になる」ことに価値があるので、
根拠のないエントリは害になる。抽出できるのは、既存ドキュメントか git 履歴に**明示的に書かれていること**だけ。

- 決定の日付は、その記述が入った commit の日付を使う（`git log --diff-filter=A --format=%as -- <file>` など）
- 抽出した決定の Status は原則 `Accepted`（既に稼働しているため）。
  ただし「検討中」「TBD」と書かれているものは `Proposed`
- 出典が曖昧なものは、抽出せずユーザーに「これは決定として記録しますか」と聞く

**件数で絞らない。** 根拠のあるものは全部拾ってよい。絞るべきなのは件数ではなく質で、
守るべき境界は1つだけ——**根拠のないエントリを1件も作らないこと**。

「たぶんこう決めたはず」「普通はこうする」で書いた行は、`git log --grep` しても何も出てこない。
そういう行が数件混じると、台帳全体が「確認しないと信じられないもの」に格下げされる。
これは初期化の最大の失敗モードなので、迷ったら書かずにユーザーへ質問として回す。

件数が多くなった場合は、削るのではなく **Epic やセクションで構造化する**（§6）。
報告では抽出件数と、根拠が弱くて見送ったものの件数を分けて伝える。

## 4. 決定の抽出元

### 既存ドキュメントから

`README.md` の技術スタック節、`ARCHITECTURE.md`、`docs/` 配下の設計文書。
「〜を採用した」「〜は使わない」と書かれている箇所がそのまま決定。

### 依存関係から（記述が無い場合の補助）

明示的な記述が無くても、リポジトリの構成自体が決定の痕跡になっている。

```bash
cat package.json 2>/dev/null | jq '{deps: .dependencies, engines: .engines, pm: .packageManager}'
ls pnpm-lock.yaml yarn.lock package-lock.json bun.lockb 2>/dev/null   # パッケージマネージャの選択
cat pyproject.toml go.mod Gemfile Cargo.toml 2>/dev/null | head -30
ls docker-compose.yml Dockerfile terraform/ 2>/dev/null                # ランタイム・インフラの選択
```

ここから起こすのは **言語 / ランタイムのバージョン / パッケージマネージャ / DB / 主要フレームワーク /
デプロイ先** くらいに絞る。ライブラリを1つずつ決定にしない（`decisions.md` の「書かなくてよいもの」に該当する）。

### git 履歴から

```bash
git log --oneline --format='%s' | rg -i 'migrat|switch|replace|adopt|drop|move to|移行|導入|採用|廃止'
```

「〜へ移行した」commit は、たいてい記録されていない決定。日付と内容が両方取れるので抽出しやすい。

## 5. タスクの抽出元

### 既存の TODO 系ファイルから

`TODO.md` `ROADMAP.md` のチェックボックスや箇条書きをそのまま Epic に振り分ける。
**完了済みの項目も `- [x]` として残す**（過去の実績が backlog の文脈になる）。

ただし §2 のとおり、**ignore されているファイルは抽出元にしない**。`TODO.md` はここで最も引っかかりやすい。

### GitHub Issues から（ユーザーが取り込みを望んだ場合のみ）

```bash
gh issue list --state open --limit 50 --json number,title,labels
```

取り込むなら、二重管理を避けるため **どちらが正か** を `{{POLICY_PATH}}` に明記する。
既定は「Issues が正、backlog は今のセッションで触る範囲だけ」。全 issue をコピーしない。
issue 番号は本文に `(#123)` として残し、追跡できるようにする。

### コード内の TODO コメントから

```bash
rg -n 'TODO|FIXME|HACK' --stats -g '!node_modules' | tail -5
```

件数だけ報告し、**自動では取り込まない**。コード内 TODO は大半がタスク化する価値のないもので、
機械的に移すと backlog が一気に腐る。件数が多い（50件超など）なら、それ自体を
「TODO コメントの棚卸し」という1タスクとして backlog に置くのが実用的。

## 6. Epic の決め方（backlog）

抽出したタスクをフラットに並べると、それだけで読みにくい台帳になる。Epic は
**リポジトリの実際の構造から取る**のが失敗しにくい——`packages/` `apps/` のディレクトリ名、
主要な機能ドメイン、あるいは `運用` `基盤` のような横断枠。

最初は **3〜5 Epic** に収まるのが理想。8を超えるなら、それ自体が分割の合図（運用ルールの分割基準に該当する）。
