# 規模の選択（backlog と decisions を独立に決める）

台帳の粒度は「小さく始めて必要になったら分割する」が原則。ただし **最初から分割すべきリポジトリもある**。
判断を誤るとどちらの方向にも痛い——早すぎる分割は空のファイルとメンテコストを増やし、遅すぎる分割は
コンフリクトと巨大ファイルを生む。

重要なのは、**backlog と decisions は増え方が違う**こと。タスクは日々増えて状態が変わるが、決定は
ゆっくり増えて不変。片方だけ分割が必要な状態はごく普通に起きるので、**2軸を独立に選ぶ**。

## 2つの軸

**backlog 軸**

| 選択 | 形 | 想定 |
|---|---|---|
| **なし** | 作らない | 課題管理が GitHub Issues / Jira 側にある。または未完了タスクが数件しかない |
| **compact**（既定） | `{{DOCS_DIR}}/backlog.md` 1ファイル・1タスク1行 | 個人〜少人数、立ち上げ期 |
| **scaled** | `{{DOCS_DIR}}/backlog/` 1タスク1ファイル + INDEX | 並行作業がある、タスクが多い |

**decisions 軸**

| 選択 | 形 | 理由の置き場 |
|---|---|---|
| **compact**（既定） | `{{DOCS_DIR}}/decisions.md` 1ファイル・1決定1行 | **commit メッセージ**（台帳は索引に徹する） |
| **scaled** | `{{DOCS_DIR}}/decisions/` 1決定1ファイル（ADR）+ INDEX | **ADR ファイル本文**（commit は trailer で ID を結ぶ役） |

**理由の置き場は decisions 軸だけで決まる。** commit メッセージの節（`assets/commit-*.md`）の選択も
これに従う。ここを混同すると「ADR にも commit にも理由が中途半端に散る」いちばん悪い状態になる。

## 判断材料

数字そのものより、**並行して触る人・エージェントがいるか** が最も効く。1ファイル台帳が最初に壊れるのは
行数ではなくコンフリクトから。

```bash
git shortlog -sn --since='6 months ago' | head        # コミッターの顔ぶれ
git log --since='3 months ago' --oneline | wc -l      # 直近の活動量
gh issue list --state open --limit 100 2>/dev/null | wc -l
ls .claude/worktrees .git/worktrees 2>/dev/null        # 並行作業の実績
ls packages apps services 2>/dev/null                  # monorepo か
ls docs/adr docs/decisions docs/rfc .claude/docs 2>/dev/null   # 既存の文書運用
```

### backlog を scaled にする条件

- ★ **複数エージェント / worktree での並行作業**を既にしている、または予定している
- **monorepo**（関心が明確に分かれ、Epic が自然に増える）
- 未完了タスクが継続的に20件前後ある、またはその見込み
- 継続的に触っている人が実質2人以上

### backlog を「なし」にする条件

- 課題管理が Issues / Jira 側で回っており、リポジトリ内に置くと二重管理になる
- 未完了タスクが数件しかなく、台帳を作っても空に近い
- 手元のタスクメモが **gitignore されている**（`TODO.md` など）。
  公開リポジトリでは、それが意図的に共有対象外にされていることが多い。**中身を移植しない**

### decisions を scaled にする条件

- ★ 既に `docs/adr/` `docs/decisions/` など **ADR の慣習がある**（形を変えると既存資産が死ぬ）
- ★ リポジトリが既に **「1トピック1ファイル + 索引表」** で内部ドキュメントを運用している。
  同じ形に揃えるほうが、新しい形を持ち込むより守られる
- 決定ごとに「却下した案」「影響」を構造的に残したい意図がユーザーにある
- 公開 OSS など、決定の経緯が外部の読み手にも参照される

コミッター数は `git shortlog` を鵜呑みにしない。AI エージェント経由の commit や co-author が混じって
実態より多く見えることがあるので、**顔ぶれを見て人数を判断する**。逆に1人でも worktree で並列に回して
いれば1ファイル台帳はすぐコンフリクトするため、人数より並行作業の有無を優先する。

迷ったら **compact**。compact → scaled の移行は ID を保ったまま機械的にできるが、
scaled → compact の縮退は情報を捨てることになる。後戻りしやすい方から始める。

### 既存の形が2択に収まらないとき

**その形を踏襲する。** 実運用では中間形態が普通に現れる。よくあるのは:

- **台帳は1ファイル1行、詳細はエリア別ファイル** — `decisions.md`（または `decisions/README.md`）が
  1決定1行の台帳で、長文が要る決定だけ `decisions/<area>.md` に本文を置く。
  台帳が1つに保たれるので `git log --grep` の起点が分散せず、compact の利点を保ったまま長文を扱える
- **移行途中で新旧が混在** — 古い決定だけ本文を持ち、ある時点以降は commit メッセージへ移した形。
  過渡期ではなく、これが安定形であることも多い

いずれも正当な理由があって選ばれている。2択に押し込めようとせず、既存の形のまま素材の節を書き換えて使う。
判断が必要なのは形式ではなく、**理由の置き場が1つに定まっているか**だけ。

## ユーザーへの示し方

AskUserQuestion で **2軸を別々の質問**にする。1問にまとめると組み合わせが6通りになり選びにくい。
推奨を第1選択肢に置き、ラベル末尾に `（推奨）` を付ける。

**推奨の根拠は description に具体的な数字で書く。** 「規模が大きいので」ではなく
「`.claude/worktrees/` に2件、内部ドキュメントが18ファイル + 索引表で運用中」と書く。
根拠が具体的だとユーザーは反証しやすく、判断が早い。

## compact → scaled への移行（既に compact で運用中のリポジトリ）

このスキルが呼ばれた時点で compact 運用済みなら、移行を提案してよい。手順:

1. **ID を保存して変換する。** `T-012` → `task-012-<kebab>.md`、`D-003` → `0003-<kebab>.md`（ADR-0003）。
   **番号は絶対に振り直さない** — commit trailer が全部無効になる
2. 旧 trailer（`Task: T-012` / `Decision: D-003`）は git 履歴に残り続けるので、
   運用ルールに「ID 対応表: `T-NNN` は `task-NNN`、`D-NNN` は `ADR-NNNN` に対応する」と1行明記する
3. compact の1行から起こせるのは title と status だけ。**Context / Consequences は commit メッセージから拾う**
   （`git log --grep='Decision: D-003'`）。拾えないものは空欄のままにし、捏造しない
4. **移行の commit には移動と変換以外の変更を混ぜない**
