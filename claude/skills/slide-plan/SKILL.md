# /slide-plan — スライド構成案（slide-plan.md）を設計する

雑多な説明から、実際に書き始められる **構成案** を組み立てる。成果物は完成スライドではなく `slide-plan.md`。
ユーザーがこの構成案に沿って中身を埋め、最終的に「slide-plan.md に従ってスライドを作成」と指示すれば
実スライド化（Marp / PowerPoint / HTML など、そのとき選ぶ形式）に進める、という橋渡しを担う。

## このスキルの守備範囲

- **やること**: 目的/聴衆の整理 → アーキタイプ（分量・トーン）決定 → ストーリー構成を複数案提示 →
  スライドごとのキーメッセージ・図解ナッジ・必要情報を書いた `slide-plan.md` の生成。
- **やらないこと**: 実際のスライド（Marp/PowerPoint/HTML/PDF）を書くこと。配色・テンプレート・ビルドは扱わない。
  それらは後段の実スライド化の守備範囲。ここでは「何をどの順で、どんな主張で、どう図解するか」まで。

構想と作図の責務を分けるのは、構成が固まる前に見た目を作ると手戻りが大きいから。
先に骨格（タイトルだけ読んで通る論旨）を固め、肉付けは後段に回す。

## 作業フロー

### 1. 入力を解釈し、不足情報を補う

ユーザーの雑多な説明から、まず次を推定・抽出する（言語化されていなければ埋める）:

- **主題**: 何についてのスライドか
- **目的**: 聞き手にどうなってほしいか（承認を得る / 行動を促す / 理解させる / 印象づける）
- **聴衆**: 誰に（経営層 / 現場 / 顧客 / 社外一般 / 技術者）。前提知識のレベル
- **利用シーン**: 投影して話す（プレゼン）か、単体で読ませる（配布・ドキュメント）か
- **制約**: 持ち時間・枚数感・締切・既存素材

推定で埋めた前提は明示し、確信が持てない核心（目的・聴衆・利用シーン・分量）は
**AskUserQuestion** で確認する。全部を聞かず、構成の分岐に効く 2〜4 点に絞る。
外部リソース（Notion 議事録・Slack・過去資料）を素材にしたい場合は、参照先をユーザーに確認してから読む。

依頼文が曖昧なほど、推定で進めると誤読が構成全体に波及する。**主題そのものの解釈が割れうる依頼**
（例:「AI開発の内製化」がAI機能開発なのかAI活用の開発プロセスなのか）では、分量やトーンより先に
**主題の定義を最優先で確認する**。ここを仮定で埋めて構成まで進むと手戻りが最も大きい。

### 2. アーキタイプ（分量・トーン）を決める

用途によって「1枚の情報量・総枚数・トーン・向いたストーリー型」が変わる。
`references/deck-archetypes.md` の一覧から、入力に合うアーキタイプを選ぶ。判断に迷う場合は
AskUserQuestion で候補を提示して選ばせる（戦略発表 / ライトニングトーク / 配布資料 / 営業提案 / 経営会議 / 勉強会 の6種）。

アーキタイプが「投影 vs 読み物」「大字・少情報 vs 精緻・自己完結」の既定値を決める。
以降の構成案はこの既定値に沿った密度で組む。

### 3. ストーリー構成を複数案つくる

同じ主題でも語り口（ストーリーライン）は複数ありうる。`references/storytelling.md` §5 のフレーム表
（SCQA / 空・雨・傘 / 課題→原因→解決→効果 / PREP / 並列・解説 / 論点網羅 / 時系列 / 結論→根拠→選択肢）から、
**性格の異なる 2〜3 案** を作る。各案について次を用意する:

- 一言でいう **構成コンセプト**（例:「課題を深掘りして解決策の必然性を出す」）
- **各スライドのタイトル（アクションタイトル＝主張文）の並び** — タイトルだけ縦読みで論旨が通ること
- 想定 **枚数** と、この案が **効く場面 / 効かない場面**
  - 持ち時間の指定があれば枚数は逆算する: **枚数 ≒ 持ち時間 ÷ 1枚あたり目安分**
    （アーキタイプの「1枚あたり」目安を使う。例: 15分 ÷ 約2分 ≒ 7〜9枚）。表紙・まとめは別枠。
    アーキタイプ既定枚数と持ち時間指定が競合したら**持ち時間指定を優先**して圧縮する

これらを **AskUserQuestion** で提示し、ユーザーに選ばせる（1案に決めきれない場合は
「案Aの流れ＋案Bの導入」のような合成も選択肢に含めてよい）。構成の良し悪しは
`references/storytelling.md` のチェック（ピラミッド構造・MECE・So What?/Why So?）で自己検証してから出す。

### 4. slide-plan.md を書く

選ばれた構成を `references/slide-plan-template.md` の形式で書き出す。
出力先は **都度ユーザーに確認する**（issues 配下作業中なら `output/slides/` が既定候補、
それ以外はカレントディレクトリ）。ファイル名は原則 `slide-plan.md`。

各スライドのセクションには、ユーザーが中身を埋められるよう **ナッジ** を書く:

- **タイトル（アクションタイトル案）**: 主張を言い切る文。目次語（「〜について」「〜の状況」）にしない。
  確定情報がなければ `[主張を埋める]` のプレースホルダ＋方向性を示す
- **キーメッセージ**: このスライドで外せない主張を 1 つ。1スライド1メッセージ
- **図解ナッジ**: この主張なら何をどう図解すべきか（`references/diagram-catalog.md` の主張型→図解の対応で選ぶ）。
  「文章で十分か図解すべきか」も判断して書く
- **必要な要素 / データ**: ユーザーが用意すべき数値・事例・引用。**出典**の欄を空けておく
  （Salesforce / GA4 / 社内DB 等、数値は出典必須）
- **補足 / スピーカーノート**（任意）: 口頭で補う想定のメモ

さらに冒頭に **必要情報チェックリスト** を置き、構成を成立させるためにユーザーが埋めるべき
情報（未確定の数値・事例・意思決定事項）を列挙する。ここが構想フェーズの主要な価値
——「何を用意すれば描けるか」を先に見せる。

### 5. 引き渡しの案内

slide-plan.md の冒頭に、実スライド化への引き渡し方法を明記する（テンプレートに含まれる）。
書き終えたら、ユーザーに「この構成案を埋めたら次は実スライド化に進める」ことと、
埋めるべきチェックリスト項目を 1〜2 行で伝える。ここでスライド本体は作らない。

## 出力の骨子（詳細は references/slide-plan-template.md）

```markdown
# スライド構成案: <主題>

> 実スライド化: 内容を埋めた上で「slide-plan.md に従ってスライドを作成」と指示（Marp / PowerPoint / HTML 等）。

## メタ / 必要情報チェックリスト
（目的・聴衆・シーン・枚数・アーキタイプ・ストーリー型／埋めるべき情報の一覧）

---
<!-- Slide 1 -->
## S1. <アクションタイトル案>
- キーメッセージ:
- 図解ナッジ:
- 必要な要素/データ（出典）:
- 補足:

---
<!-- Slide 2 --> ...
```

`---` 区切りで 1 セクション＝1 スライドに対応させ、後段の実スライド化にそのまま渡せる形にする。

## 参照ファイル

- `references/deck-archetypes.md` — 用途別の分量・トーン・枚数・向いたストーリー型の既定値
- `references/storytelling.md` — 構成・ロジック設計（ピラミッド / MECE / SCQA / 空雨傘 / アクションタイトル / So What?・Why So?）
- `references/diagram-catalog.md` — 主張の型 → 適した図解の対応表、文章 vs 図解の判断、レイアウト基本
- `references/slide-plan-template.md` — slide-plan.md の出力テンプレート（そのまま複製して使う）

## ユーザー起動

- `/slide-plan <どんなスライドを作りたいかの雑多な説明>` — 説明を解釈して構成案づくりを開始
- `/slide-plan` — 何のスライドかをまず対話で聞き出してから開始
