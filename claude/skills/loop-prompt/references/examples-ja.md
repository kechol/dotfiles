# 完成例

生成の粒度・トーンの基準。実際はタスクに応じて節を増減し、検証・停止句は必要分だけ選ぶ。

## 例 1: /goal モード（テスト全通過まで移行を完遂）

### 入力（ノイズ多め）

> えー、認証まわりのやつを新しい API に移したくて、payment って古いクライアント使ってるとこ全部。で、テスト通ればオッケーなんだけど、途中でテスト消したりされると困るし、他のモジュール巻き込まないでほしい。まあ放っといても終わってくれると助かる。

### 出力（本体 → 起動行の順で貼る）

```md
# 依頼: payment モジュールの認証呼び出しを新 API へ移行し、テストが全て通る状態にする

## 背景
旧認証クライアントを廃止するための移行です。payment の全呼び出し箇所を新 API に置き換え、既存の振る舞いを保ったままテストを緑にすることがゴールです。人が張り付かず完遂させたい。

## あなたの役割
あなたはこのタスクを自律的に完遂するエンジニアで、認証基盤に精通しています。各サイクルで残りの呼び出し箇所を確認し、1 箇所ずつ新 API に移し、独立した検証で裏を取ってから次へ進んでください。

## 作業手順
1. 旧クライアントの呼び出し箇所を洗い出し、残数を IMPLEMENTATION_PLAN.md に記録する。
2. 次の 1 箇所を新 API に移す。振る舞いは変えない。
3. 新しいコンテキストの検証サブエージェントを起動し、差分とテスト結果を仕様に照らして「見せかけの完了」が無いか確認させる。
4. 緑になったらコミットし、IMPLEMENTATION_PLAN.md の残数を更新する。

## 出力
- 各サイクル: 移行 1 箇所分のコミットと、IMPLEMENTATION_PLAN.md の進捗更新。

## 禁止事項
- テストの削除・アサーションの緩和をしない。エラーを握りつぶさない。
- payment 以外のモジュールを変更しない（Never touch）。
- 「ついで」のリファクタや整理をしない。移行に必要な変更だけ。

## 検証
- 各コード変更後、独立した検証サブエージェントで、旧 API 呼び出しが残っていないか・既存テストが緑か・見せかけの完了が無いかを定量的に確認する。
- 進捗は必ずツール結果（テスト出力）に照らして報告する。緑でないなら緑でないと言う。

## 完了条件 / 中断条件
- 完了（Done when）: payment 内に旧 API 呼び出しが 0 件、かつ全テストが通過。
- 中断（Stop if）: payment 外のファイル変更が必要になった、既存の通過テストが新たに失敗して原因不明、破壊的操作が必要になった。
```

起動行:

```
/goal payment モジュールに旧認証 API の呼び出しが 0 件で、npm test が 0 で終了する。証明は grep で旧クライアント参照が無いことと npm test の出力。payment 以外のテストファイルは変更しない。または 30 ターンで停止。
```

## 例 2: /loop モード（定期トリアージ）

### 入力

> 毎朝、#project-feedback のバグ報告を見て、トリアージして、その日の分は全部対応か返信までしてほしいんだよね。

### 出力（本体 → 起動行）

```md
# 依頼: #project-feedback のバグ報告を定期的にトリアージし、当日分を全て捌く

## あなたの役割
あなたはサポートとエンジニアリングを橋渡しする担当です。各実行で新規報告を読み、重大度で分類し、対応または返信まで持っていってください。

## 作業手順
1. #project-feedback の前回実行以降の新規報告を読む。
2. 各報告を「バグ / 要望 / 質問」と重大度で分類し、状態ファイルに記録する。
3. バグは修正方針を立てて対応、質問・要望は返信。判断に迷うものは人に上げる。

## 出力
- 分類結果と対応状況の一覧（状態ファイル）。返信・起票した内容。

## 禁止事項
- 未確認の推測で「解決済み」と返信しない。
- 本番に影響する変更を確認なしに行わない。

## 検証
- 「対応済み」とする前に、実際に返信・起票・修正が行われた証拠（リンク・ID）を確認する。証拠を示せないものは未対応として残す。

## 完了条件 / 中断条件
- 完了（Done when）: 今回見つけた報告が全て、分類・対応/返信済み。
- 中断（Stop if）: 本番影響のある修正が必要、または判断が担当者マターの報告に当たった。
```

起動行:

```
/loop 1h #project-feedback の新規バグ報告を読み、分類し、当回で見つけた分は全てトリアージ・対応・返信まで終えるまで止まらない。本番影響のある変更が必要なときは止めて確認する。
```

## 例 3: Skill 変換モード（明示指示があったときだけ）

「この dep 更新の Skill を loop 対応にして」のような指示で、既存 SKILL.md に次を加える:

- **検証節**: 更新後、独立サブエージェントでビルド・テスト・型チェックが通るか、破壊的変更が無いかを確認。
- **停止条件節**: 完了 = 対象パッケージが全て更新されテスト緑。中断 = メジャー更新で破壊的変更が出た、テストが直せない。上限ターン。
- **状態外部化**: 更新対象と結果を `deps-progress.md` に記録し毎サイクル再読。
- **description 更新**: loop/goal 前提であることと「dep 更新を自動で回して」等のトリガーを反映。

元の意図・手順は保ち、検証と停止条件を足すだけに留める（過剰なリファクタはしない）。
