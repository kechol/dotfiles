# loop の検証と停止条件 設計図

生成する loop プロンプトの心臓部。ここから必要な型・句を選んで組み込む。全部入れず、タスクに要る分だけ。

## なぜ独立検証が要るか

> コードを書いたモデルは、自分の宿題を採点するには優しすぎる。

作った本人に「できた？」と聞くと通ってしまう。loop は人が張り付かない前提なので、信頼できる検証者だけが「離席してよい」根拠になる。だから実装と検証を**別コンテキスト・別エージェント**に分け、検証者は既定で「壊れているとみなす」姿勢を取る。`/goal` の評価モデルが実装モデルと別なのも同じ理由。

## 独立検証サブエージェントのテンプレート

生成プロンプトの検証節に、この趣旨を埋め込む（Claude Code なら Agent tool で `model: 'sonnet'` か `'haiku'`、read 系ツールのみ）。

> 各サイクルのコード変更後、新しいコンテキストの検証サブエージェントを起動してください。検証者の姿勢は「このコードは壊れている」。仕様（完了条件）と実際の差分・テスト結果を突き合わせ、下の「見せかけの完了」に該当する近道が使われていないか確認させてください。検証者は修正も実行もせず、次の純粋な JSON だけを返します:
> `{"passes": <bool>, "failures": [{"where": "<場所>", "shortcut": "<該当した近道>", "why": "<なぜ不合格か>"}]}`
> `passes` が false の間は loop を継続し、failures を次サイクルの指針にしてください。

## 「見せかけの完了」11 類型（検証チェックリスト）

検証者にこれらを潰させる。「編集が成功した」「1 つテストが通った」だけを完了扱いにしない。

1. **テストの緩和** — アサーションの削除や `expect` の骨抜きで通す。
2. **エラーの握りつぶし** — try/catch で握って握って握りつぶし、失敗を隠す。
3. **名前だけ変更** — リネームやコメント変更で「直した風」、挙動は未変更。
4. **スタブ返却** — 特定テストだけ通るハードコード値を返す。
5. **TODO 化** — バグを直さずコメント（TODO/FIXME）に退避しただけ。
6. **ハッピーパスのみ** — 正常系だけ実装し、エラー系・空入力・境界を無視。
7. **スコープ超過** — 目標外のファイルまで変更が混入（「ついで直し」）。
8. **存在しない API** — 実在しない関数・引数を使い、動く前提で書く。
9. **無言の設計変更** — スキーマ・認証・公開 API を黙って変え、影響を報告しない。
10. **自己完結モック** — 実物でなくモック同士でだけ通るテスト。
11. **別問題を解いた完了** — 目標と違う問題を解いて「done」と称する。

## `/goal` 完了条件の書き方

評価モデルは会話に現れた証拠しか見ない（ツールを実行しない）。ゆえに条件は Claude 自身の出力で証明できる形にする。良い条件は 3 つを備える:

- **測定可能な終着点 1 つ** — テスト結果、ビルド終了コード、ファイル数、空のキュー。
- **証明方法** — どう示すか。「`npm test` が 0 で終了」「`git status` がクリーン」。
- **守るべき制約** — 到達の途中で変えてはいけないもの。「他のテストファイルは変更しない」。

実行時間を縛るには「または N ターンで停止」「または X 分で停止」を条件に含める。条件は 4000 文字まで。

**良い例:**
> `/goal test/auth のテストが全て通り lint がクリーン。証明は npm test と npm run lint が共に 0 で終了。他のテストファイルは変更しない。または 20 ターンで停止。`

**弱い例（評価不能・曖昧）:**
> `/goal 認証まわりをいい感じにする`（終着点も証明方法も無い）

## 停止条件の 4 点セット

生成プロンプトに必ず含める:

- **Done when（完了）**: 機械的に判定できる終着点。
- **Stop if（中断）**: 人を呼ぶべき事象 — スコープ外変更が N 件超、通過済みテストの新規失敗、不可逆・破壊的操作の必要、ユーザーにしか出せない入力。
- **ターン/時間上限**: 無限ループの保険。
- **人を残す**: 完全放任にしない。重要な判断では止まって確認させる（cognitive surrender を避ける）。

## 状態の外部化（長時間 loop）

コンテキストに目標や進捗を抱えると数サイクルでドリフトし、トランスクリプトが膨れて精度が崖落ちする（context rot）。状態はディスクに出し、毎サイクル再読させる。

- `IMPLEMENTATION_PLAN.md`（自由記述）— 進捗と次の一手。`STATUS: done` で loop 終了の合図にできる。
- `tests.json`（構造化）— テストの通過状況など、スキーマがある情報。
- `MEMORY.md`（自由記述）— セッション横断の決定・好み・直近フィードバックだけ。肥大化させない。
- **git** — チェックポイントと履歴。緑になったらコミット。

> 各サイクルの冒頭で状態ファイルを読み、末尾で更新してください。終わったサブタスクの詳細はコンテキストに残さず、状態ファイルに要約して捨ててください。

## トークンとアンチパターン

- 小さなタスクに loop やサブエージェントは要らない。推論よりスクリプト実行の方が安い。
- CLAUDE.md / プロンプトを肥大化させない（毎ターンのコストになる）。1 段落 = 全サイクルへの課金。
- 「ついで直し」を禁じる。One change, one purpose。
- 自動化を信頼しすぎない。理解の負債（自分が書いていないコードが積み上がる）を避け、設計者であり続ける。
