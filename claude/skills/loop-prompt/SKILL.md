# loop-prompt

曖昧なタスク指示や loop 非対応のプロンプト/Skill を、**Claude Code で自律実行できる loop プロンプト**に変換する。入力（変換したいタスク指示や既存プロンプト/Skill）はこのスキルの引数、または直前のユーザー発話として渡される。あなたは「設計役」であり、タスク自体は実行しない。成果物は、ユーザーがそのまま起動できる loop プロンプト（日本語）である。

loop の要は 2 つ — **検証**（作った本人に採点させない）と**停止条件**（いつ終わる/中断するかを事前に宣言する）。この 2 つが無い loop は、静かに壊れたコードを量産するか、永遠に止まらない。だからこのスキルは、この 2 つを必ず埋め込む。

## Step 1. loop 適性を判定する（最初にやる）

何でも loop 化してよいわけではない。次を確認し、**loop に向かないなら正直にそう伝えて通常プロンプトを勧める**。無理に loop 化しない。

- **完了を機械的に判定できるか。** テスト通過・ビルド成功・ファイル数・キューが空、など「できた」を証拠で示せるか。示せないなら `/goal` は機能しない（評価者は会話に現れた証拠しか見ない）。
- **反復性か長時間性があるか。** 毎朝のトリアージ、CI 失敗の修正、多数の呼び出し箇所の移行など、人が張り付かず回す価値があるか。単発・数分で終わる作業に loop は過剰。
- **探索的すぎないか。** 「良い設計を考えて」のような発散タスクは、完了条件が定まらず loop に向かない。

判定に迷う要素（完了条件が言語化できない等）があれば、`AskUserQuestion` で確認してから進む。

## Step 2. loop 種別を選ぶ

Claude Code には停止のさせ方が異なる 3 つの仕組みがある。**次のターンを何が始めるか**で選ぶ。

| 仕組み | 次ターンの起点 | 停止条件 | 向くタスク |
| --- | --- | --- | --- |
| `/goal <条件>` | 前ターンの完了 | 評価モデルが完了条件を満たしたと判定 | 検証可能な終着点まで走り切る作業（テスト全通過まで移行、受け入れ基準を全て満たすまで実装） |
| `/loop <間隔> <指示>` | 一定時間の経過 | ユーザーが止める / Claude が完了と判断 | 定期的・反復的な作業（毎朝の要約、PR の監視と対応） |
| 併用 | `/loop` で起動しつつ「〜まで止まるな」で goal 的に縛る | 両方 | 定期起動 × 「今回見つけた分は全部片付くまで」 |

複数の種別が妥当で選べないときは、`AskUserQuestion` でユーザーに確認する（例: 「完了したら止める（/goal）」か「一定間隔で回し続ける（/loop）」か）。

`/goal` は評価者（既定は Haiku 等の小型モデル）が**毎ターン後に会話内容だけを見て**完了を判定する。評価者はツールを実行せずファイルも読まない。ゆえに完了条件は「Claude 自身の出力で証明できる」形にする（例: Claude がテストを走らせ、その結果が会話に出る）。

## Step 3. タスクを意図に還元する

入力（多くはノイズの多い音声メモ）を読み、次を抽出する。原文の言い回しでなく**何を達成したいか**を掴む。

- **目的**: 最終的に何が成れば良いか（1 文で言い切れるか）
- **完了条件（Done when）**: どうなったら「終わり」か。機械的に判定できる形にする
- **対象範囲と禁則（Never touch）**: 触ってよい領域と、絶対に変えてはいけないもの
- **中断条件（Stop if）**: 何が起きたら人を呼ぶ/止まるべきか（スコープ外変更の多発、既存テストの新規失敗など）
- **背景（なぜ）**: 誰のための、何に繋がる作業か（意図が分かると Claude は正しく判断できる）
- **検証手段**: 完了を何で確かめるか（テスト、Lint、スクリーンショット、独立レビュー）

## Step 4. 検証と停止条件を設計する

ここが loop の心臓部。詳細な手法・テンプレートは `references/verification-ja.md` を参照して設計する。要点:

- **作った本人に採点させない。** 実装と検証を分け、**独立した検証サブエージェント**（別コンテキスト・別モデル、既定「壊れているとみなす」姿勢）に仕様と突き合わせさせる。自己批判より精度が高い。
- **定量チェックを優先する。** テスト終了コード・スコア閾値・件数など、数値で判定できるほど Claude は自己検証しやすい。
- **見せかけの完了を潰す。** テストの緩和、エラー握りつぶし、ハードコードでのテスト通過など「フェイク完了」の典型（`references/verification-ja.md` の一覧）を検証項目に含める。「編集が成功した」だけで完了扱いにしない。
- **停止条件を事前宣言する。** Done when（完了）/ Stop if（中断）/ ターン上限（`または N ターンで停止`）を必ず書く。実行中に基準を判断させるとぶれる。
- **長い loop は状態をディスクに出す。** 進捗・決定・記憶を `IMPLEMENTATION_PLAN.md` 等のファイルに書かせ、コンテキストを軽く保つ（context rot を避ける）。

## Step 5. loop プロンプトを生成する

下のテンプレートに沿って日本語で生成する。プロンプト本体（文脈を作る指示）と、起動行（`/goal` または `/loop`）の 2 部構成にする。該当しない節は削り、空節を作らない。定型の検証・停止句は `references/verification-ja.md` から必要分だけ選ぶ（入れ過ぎない）。

生成物はチャットにコードブロックで提示する。本体と起動行が分かるようにし、末尾に「本体を貼って文脈を作ってから起動行を実行」と貼り方を 1〜2 行添える。

### 出力テンプレート（/goal モード）

```md
# 依頼: {一文で言い切る目的}

## 背景
{誰のための、何に繋がる作業か。なぜ今か。1〜3文}

## あなたの役割
あなたはこのタスクを自律的に完遂するエンジニアです。各サイクルで {対象の状態} を確認し、完了条件に近づける一手を打ち、独立した検証で裏を取ってから次に進んでください。
{タスク固有の専門性を一言。例: 「あなたは認証基盤に精通しています」}

## 作業手順
1. {現状把握。多くは対象と仕様の確定}
2. {完了条件に向けた一手}
3. {検証。独立した検証サブエージェントで仕様に照らす。定量チェックを使う}
4. {緑になったらコミット等の確定。進捗を状態ファイルに記録}

## 出力
{各サイクルで何を残すか。コミット、状態ファイルの更新、要約の粒度}

## 禁止事項
{触れてはいけない領域（Never touch）。テストの削除・緩和、エラー握りつぶし、スコープ外の「ついで直し」の禁止}

## 検証
{完了を何で証明するか。「新しいコンテキストの検証サブエージェントで仕様と突き合わせ、見せかけの完了が無いか確認」。進捗はツール結果に照らして報告}

## 完了条件 / 中断条件
- 完了（Done when）: {機械的に判定できる終着点}
- 中断（Stop if）: {人を呼ぶべき事象。スコープ外変更の多発、既存テストの新規失敗など}
```

起動行:

```
/goal {測定可能な完了条件}。証明方法は {npm test が 0 で終了 等}。{変えてはいけない制約}。または {N} ターンで停止。
```

### 出力テンプレート（/loop モード）

本体は上と同様（役割・手順・出力・禁止・検証を簡潔に）。起動行:

```
/loop {間隔（例 1h）} {毎回やること}。{今回分を全部片付けるまで止まらない、等の goal 的縛り}。{中断条件}。
```

## 品質基準（貼り出す前に必ず確認）

生成物が次を満たすか確認し、満たさなければ直す。これがこのスキルの品質基準:

- **人格・作業手順・出力・禁止がある。** 自律実行者として 1 サイクル（把握 → 一手 → 検証 → 確定）を自分で回せる形か。各サイクルの成果物と状態の記録先が書かれ、禁止に Never touch とフェイク完了の近道が入っているか。
- **検証がある（無ければ不合格）。** 作った本人以外の独立サブエージェントが、定量的に、見せかけの完了を疑って確かめる設計か。
- **停止条件がある（無ければ不合格）。** 完了（Done when）・中断（Stop if）・ターン上限が明記され、`/goal` の完了条件は Claude の出力で証明できる形か。
- **背景（なぜ）がある。** 意図が伝わり、Claude が自力で判断できるか。
- **loop 適性がある。** そもそも loop 向きのタスクか（Step 1 を再確認）。向かないなら loop 化せず通常プロンプトを勧めたか。
- **人を残しているか。** 完全放任にせず、不可逆操作やスコープ変更では止まって確認する設計か。

## Skill 変換モード（明示指示があるときだけ）

ユーザーが「この Skill を loop 対応にして」と明示したときのみ、既存 SKILL.md を loop-ready に書き換える（作成・編集する）。やること:

- 検証節を足す（独立検証サブエージェントの手順、定量チェック、見せかけ完了対策）。
- 停止条件節を足す（Done when / Stop if / ターン上限）。
- 長時間 loop 向けに状態の外部化（進捗をファイルに記録し毎サイクル再読）を指示。
- description に loop/goal 前提であることと発動トリガーを反映。
- 既存の意図・トーンは保つ。過剰なリファクタはしない。
